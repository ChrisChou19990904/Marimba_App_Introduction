💡 1. 數位音訊合成與轉調原理

本網頁底層基於 Tone.js 網頁音訊架構（Web Audio API），核心運作包含以下物理與數學邏輯：

(1) JavaScript 即時轉調演算法

在數位音樂（MIDI）協議中，每個音階都對應一個 0 到 127 的整數 MIDI Number。
本程式透過算術運算達成即時轉調：在音符觸發前執行 note.midi + transpose。
例如：原本演奏錄製的 C4 (MIDI 編號 60) 加上 3 個半音（transpose = 3），數值會變為 63 (D#4)，再由音訊引擎將該編號換算成對應的物理頻率（Hz）發聲。

(2) 波形合成（Oscillator）與包絡線（Envelope）

網頁能切換不同的聲音類型，是透過改變訊號產生器（Oscillator）的物理波形與振幅包絡線（ADSR Envelope）來模擬不同樂器的聽感：

  • 圓潤鋼琴風 (Triangle)：使用三角形波。其奇數諧波衰減極快，音色相對圓潤純淨。搭配快攻擊（Attack）、長釋放（Release）的包絡線，能有效模擬鋼琴或打擊樂器敲擊後餘音繚繞的物理動態。
  • 明亮電子琴 (Sawtooth)：使用鋸齒波。它包含了所有的連續諧波，聲音非常明亮且飽滿，是 80 年代昭和特攝電子合成器（Synthesizer）最經典的標誌性音色。
  • 復古 8-bit (Square)：使用方波。僅包含強烈的奇數諧波，聲音生硬且帶有強烈的數位感，能完美還原早期紅白機（NES）遊戲音樂的復古氛圍。
  • 柔和純音 (Sine)：使用正弦波。它是最純粹的單一頻率基音，沒有任何諧波成分，聽感極度平滑。

📊 2. 聲學可視化與時間軸排程控制原理

為了克服純音訊播放時「看不見數據流動」與「無法自由掌控播放時間」的限制，本架構引入了 Web Audio API 的進階分析節點與排程引擎：

(1) 示波器波形圖（Tone.Waveform）：時域分析

Tone.Waveform 能夠以每秒數十次的頻率捕捉訊號的時間域振幅（Time-Domain Amplitude）。程式將採集到的 -1.0 至 1.0 浮點數陣列映射至 Canvas 畫布的 Y 軸座標，繪製出連續振動的聲波線條。讀者可以直觀看見三角波的平緩折角、方波的垂直陡升，以及正弦波的柔和圓弧。

(2) 頻譜分析儀（Tone.FFT）：頻率域分析

Tone.FFT 透過快速傅立葉變換，將複雜的音訊訊號拆解為各頻率成分的能量分貝值（dB）。畫面左側代表低音貝斯（Bass）能量，右側代表高音與泛音（Treble）。當播放明亮的鋸齒波時，右側高頻柱會活躍跳動；轉調時，整個能量群則會即時水平平移。

(3) Tone.Transport 與 Tone.Part：非阻塞式時間軸主控

傳統做法如果直接呼叫 triggerAttackRelease，會將所有音符一次性鎖死在硬體時鐘上，導致無法暫停與拖曳。本系統改寫為：

  • 時間座標抽象化：將整首曲目的音符解析為帶有時間標籤的事件群組，載入至 Tone.Part。
  • 主控時鐘掛載：由 Tone.Transport 統籌全域播放指針。按下暫停時，僅需凍結時鐘並呼叫 releaseAll() 釋放發聲，即可完全不漏拍地保留當前播放進度。
  • 任意跳轉（Seek）：拖曳進度條時，透過更新 Tone.Transport.seconds 數值，即時對齊時間指針，達成流暢的快進與倒帶。

📱 3. 行動裝置瀏覽發聲重要提示與 Web Audio 底層原理

⚠️ 行動裝置瀏覽重要提示：
當你使用手機瀏覽本網頁時，請務必將手機側邊的「實體靜音開關」切換至響鈴模式（並確認非震動/勿擾狀態），否則網頁會完全沒有聲音。

💡 為什麼開啟靜音模式會導致網頁沒聲音？（技術原理探討）
本網頁是利用 HTML5 的 AudioContext（Web Audio API）在前端即時動態運算並合成物理波形。在 iOS（WebKit 核心）與部分 Android 系統的底層音訊通道設計（Audio Session Category）中，網頁端即時合成的音訊預設會被標記為 Ambient（環境音效）或次要媒體類別。

當手機開啟實體靜音鍵時，行動作業系統為了不干擾使用者，會在硬體層級強制壓制所有 Ambient 類別的音訊輸出（如同手機遊戲的背景音效會在靜音模式下被切斷，但 YouTube 等預錄影片所使用的 Playback 類別音訊不會被切斷）。因此，這並非程式出錯，而是作業系統的硬體機制攔截。點擊播放前請確保已切換為響鈴狀態！

⚠️ 4. 核心觀點：技術無法取代演奏能力與「分治工程實踐」

雖然程式可以透過演算法輕鬆改變調性與音色，但「優質的旋律數據」必須源於真實且紮實的演奏功底。
本網頁所展示的 52 首精選旋律，皆是我本人純手工在行動裝置狹小的螢幕上，完全僅憑「左手大拇指與右手大拇指」的極限協調，在 Perfect Piano 中開啟 MIDI 錄製模式辛苦彈奏而成，絕非使用網路上現成的數位音訊檔案。

在小螢幕上以雙拇指精準駕馭如《魔彈戰記龍劍道》或《假面騎士 Build》等每分鐘超過 130 拍（BPM）、音符密度極高的快節奏特攝曲目，要求創作者具備極高的節奏感、動態掌控力與鍵位空間感。這些親自演奏錄製的 MIDI 數據，完整保留了人類演奏特有的細微情感，是純程式動態生成或死板的 Q 點量化所無法比擬的。

🛠️ 長曲目演奏的人體工學瓶頸與 Python 分治實踐（三段式 Take）

在手機觸控螢幕上彈奏長篇曲目時，面臨的並非技術問題，而是人體工學極限與容錯率的嚴苛考驗：

  • 生理疲勞與單點故障：觸控螢幕缺乏物理琴鍵的觸覺回饋，像《七龍珠 GT》神曲《漸漸被你吸引》時長數分鐘、伴奏聲部繁複，長時間高速敲擊極易導致拇指僵硬；只要在最後數秒按偏一個音，整條錄音就直接作廢。
  • 分治策略（Divide and Conquer）：為確保每一段落的力度與時序皆處於最佳狀態，我將長曲目依結構拆解為數個 Take 分段錄音（如《漸漸被你吸引》三段 Take）。
  • 剪除停頓與時間軸緊密重構：分段錄音常伴隨「按下錄音至敲鍵」以及「彈奏結束至按停」的發呆空白。透過 Python 腳本動態計算每個片段的第一個與最後一個音符事件，自動剔除多餘空檔，並跨軌道提取 Note On/Off 訊息重算 Delta Time，重構出無縫緊湊的完整音軌。
💻 三段式長曲目自動無縫合併實作（以《漸漸被你吸引》為例）：

1. 安裝所需套件：

pip install mido

2. 執行三段合併腳本（merge.py）：

import mido

# 依序填入需要串接的分段 MIDI 檔案名稱
files = [
    "漸漸被你吸引.mid",
    "漸漸被你吸引2.mid",
    "漸漸被你吸引3.mid"
]
output_file = "漸漸被你吸引_完整版.mid"

# 銜接間隔緩衝設定（0.05 秒微呼吸感，徹底消除錄音反應延遲）
GAP_SECONDS = 0.05

# 1. 初始化輸出物件與標準 120 BPM 基準
merged_mid = mido.MidiFile(ticks_per_beat=480)
merged_track = mido.MidiTrack()
merged_mid.tracks.append(merged_track)
merged_track.append(mido.MetaMessage('set_tempo', tempo=500000, time=0))

all_notes = []
current_timeline = 0.0

# 2. 跨軌道解析物理時間，並自動剪除錄製前後的空檔
for idx, f in enumerate(files):
    mid = mido.MidiFile(f)
    segment_events = []
    abs_time = 0.0

    # 提取音符事件與累積絕對秒數
    for msg in mid:
        abs_time += msg.time
        if msg.type in ['note_on', 'note_off']:
            segment_events.append((abs_time, msg.copy()))

    if not segment_events:
        continue

    # 計算有效演奏區間：消除開頭等待起手與結尾按停的空白
    first_note_time = segment_events[0][0]
    last_note_time = segment_events[-1][0]

    for note_time, msg in segment_events:
        aligned_time = current_timeline + (note_time - first_note_time)
        all_notes.append((aligned_time, msg))

    actual_duration = last_note_time - first_note_time
    current_timeline += actual_duration + GAP_SECONDS

# 3. 依絕對物理時間重排，並還原為 MIDI Delta Time
all_notes.sort(key=lambda x: x[0])
last_time = 0.0

for note_time, msg in all_notes:
    delta_sec = note_time - last_time
    delta_ticks = int(mido.second2tick(delta_sec, ticks_per_beat=480, tempo=500000))
    msg.time = delta_ticks
    merged_track.append(msg)
    last_time = note_time

merged_track.append(mido.MetaMessage('end_of_track', time=0))
merged_mid.save(output_file)
print(f"🎉 無縫拼接完成：{output_file}，最終時長：{merged_mid.length:.2f} 秒")

🔍 日文 Unicode 編碼地雷與檔案系統避坑實務（二段式 Take）

在處理特攝曲（如《ジードの証》）、動漫日文歌名時，許多創作者在寫 Python 批次處理或網頁加載時，常會撞見這個令人抓狂的靈異現象：
「程式明明照著檔案名稱寫，控制台卻一直噴 FileNotFoundError: [Errno 2] No such file or directory: 'ジードの証.mid'，甚至複製貼上到編輯器後，字元之間莫名其妙跑出宛如按了空白鍵的空檔？」

📌 為什麼會有這層幽靈空格與找不到檔案？（底層原理拆解）：
  1. Unicode NFC（合成形式）vs NFD（分解形式）標準衝突： 在國際編碼規範中，日文的濁音（如 ジ、ガ）與半濁音（如 パ）有兩種合法的表達方式：
    • NFC（Canonical Composition）：把「基本字元」與「濁點 ゛」融合成單一 Unicode 碼位。例如 ジ 就是單一字元 \u30b8（Windows 系統預設、網頁 URL 常見格式）。
    • NFD（Canonical Decomposition）：把字元拆成「基底文字 + 獨立結合濁音符號（Combining Character）」。例如 ジ 被拆成了「シ (\u30b7)」加上獨立濁音符號「゛(\u3099)」兩個字節（macOS 檔案系統或特定通訊軟體剪貼簿常見格式）。
  2. 字型引擎的「幽靈空格」假象： 當帶有 NFD 格式的檔名字串被複製到某些終端機（如 PowerShell）或不完全支援結合字元對齊的文字框時，渲染引擎無法精確把濁點疊加在假名右上角，而是把它獨立當作一個全形或半形字元渲染出來，外觀上就像多了一個「删不掉的空白鍵」！
  3. 作業系統的「二進位逐字節比對」失敗： 在人類肉眼看來，NFC 的 ジ 與 NFD 的 シ + ゛ 完全一模一樣；但對 Windows 檔案系統（特別是繁體中文預設為 CP950/Big5 語系）或 Python 核心來說，二進位 byte 根本不同。Python 拿著 NFD 去硬碟找 NFC 檔案，自然無情報錯 FileNotFoundError。
💡 工程解決方案（雙管齊下）：
  • 架構解法（最佳實踐）：「後台管線 ASCII-Safe，前台介面 Localized」。批次處理腳本與伺服器二進位儲存檔名一律命名為純英數（如 Geed_part1.mid、Geed_part2.mid、Geed_No_Akashi_Full.mid），避開所有 OS I/O 與瀏覽器 fetch URL 編碼雷區；而「ジードの証」則保留在前端畫面的按鈕標題純作視覺展示。
  • 程式碼解法（若非得讀取日文檔名）：使用 Python 內建的 unicodedata.normalize('NFC', filename) 將字串強制收斂為單一合成字元，即可正常讀取。
💻 專用雙檔合併工具與編碼安全管線（以《超人力霸王捷德》二合一為例）：

針對主副歌二段式 Take，且避開日文假名濁音/促音編碼衝突的獨立腳本（merge_two.py）：

import sys
import unicodedata
import mido

# 強制輸出為 UTF-8，防止 PowerShell / CMD 終端機日文字元輸出衝撞
sys.stdout.reconfigure(encoding='utf-8')

# 採用 ASCII-Safe 命名（亦可搭配 unicodedata.normalize('NFC', ...) 處理）
FILE_A = "Geed No Akashi.mid"
FILE_B = "Geed_part2.mid"
OUTPUT_FILE = "Geed_No_Akashi_Full.mid"
GAP_SECONDS = 0.1

files = [unicodedata.normalize('NFC', FILE_A), unicodedata.normalize('NFC', FILE_B)]
merged_mid = mido.MidiFile(type=0, ticks_per_beat=480)
merged_track = mido.MidiTrack()
merged_mid.tracks.append(merged_track)
merged_track.append(mido.MetaMessage('set_tempo', tempo=500000, time=0))

all_notes, current_timeline = [], 0.0

for idx, f in enumerate(files):
    mid = mido.MidiFile(f)
    segment_events, abs_time = [], 0.0
    for msg in mid:
        abs_time += msg.time
        if msg.type in ['note_on', 'note_off']:
            segment_events.append((abs_time, msg.copy()))

    if not segment_events: continue
    first_time, last_time = segment_events[0][0], segment_events[-1][0]
    for note_time, msg in segment_events:
        all_notes.append((current_timeline + (note_time - first_time), msg))

    actual_duration = last_time - first_time
    current_timeline += actual_duration + GAP_SECONDS

all_notes.sort(key=lambda x: x[0])
last_time = 0.0
for note_time, msg in all_notes:
    delta_ticks = int(mido.second2tick(max(0.0, note_time - last_time), ticks_per_beat=480, tempo=500000))
    msg.time = delta_ticks
    merged_track.append(msg)
    last_time = note_time

merged_track.append(mido.MetaMessage('end_of_track', time=0))
merged_mid.save(OUTPUT_FILE)
print(f"🎉 捷德雙檔無縫合併完成：{OUTPUT_FILE}，總長度：{merged_mid.length:.2f} 秒")

🎼 極致複雜樂句拆解與交響呼吸感調校（以《光的戰役》8 段 Take 為例）

如果說《七龍珠 GT》是長曲目的耐力考驗，那麼國產特攝經典《鎧甲勇士》片尾曲《光的戰役》則是指法複雜度與聲部密度的極限挑戰：

  • 多層次樂句拆解（8 個 Take）：全曲長達兩分鐘，前奏的交響動態變化極多，尾奏收尾切分音繁複，極度考驗手指靈活度。為了確保每個變奏與和弦的精準度，我採取更細緻的分治架構，將全曲拆解為 8 個錄音片段（前奏 5 段、正式演奏 2 段、結尾 1 段）[cite: 1]。
  • 交響呼吸感與段落留白（Gap Padding）：樂章之間並非零間隔貼合，為了保留原曲交響推進的蓄力感與休止符，我在腳本中刻意設定了 GAP_SECONDS = 0.5 秒的銜接空檔。
  • 累積時長物理分析：8 個片段共產生 7 個銜接點（累積貢獻 $7 \times 0.5 = 3.5$ 秒的人工留白），加上各段演奏末尾自然的釋音延音（Release），最終合併長度約 2 分 10 秒（剛好比原版多出約 10 秒），完美還原了交響戰歌該有的呼吸感與磅礴張力。
  • 管線輸出與手動命名規範：為確保 Python 在處理大量檔案串接時不受編碼干擾，腳本初期先輸出為 ASCII-Safe 的過渡檔名 Battle_of_Light_Full.mid；生成確認無誤後，直接在檔案總管按滑鼠右鍵重新命名為「光的戰役.mid」，與下方播放清單的 fetchAndPlayMidi('光的戰役.mid') 調用路徑完美對齊。
💻 《光的戰役》8 段專用合併腳本（merge_battle_of_light.py）： 
import sys
import unicodedata
import mido

sys.stdout.reconfigure(encoding='utf-8')

# 依序填入 8 個分段錄音檔名
files = [
    "光的戰役前奏.mid",
    "光的戰役前奏2.mid",
    "光的戰役前奏3.mid",
    "光的戰役前奏4.mid",
    "光的戰役前奏5.mid",
    "光的戰役正式片段.mid",
    "光的戰役正式片段2.mid",
    "光的戰役結尾.mid"
]
# 先行輸出為英文安全檔名，產出後再按右鍵重新命名為「光的戰役.mid」
OUTPUT_FILE = "Battle_of_Light_Full.mid"
GAP_SECONDS = 0.5  # 刻意保留 0.5 秒交響蓄力呼吸感

merged_mid = mido.MidiFile(type=0, ticks_per_beat=480)
merged_track = mido.MidiTrack()
merged_mid.tracks.append(merged_track)
merged_track.append(mido.MetaMessage('set_tempo', tempo=500000, time=0))

all_notes, current_timeline = [], 0.0

for idx, filename in enumerate(files):
    normalized_name = unicodedata.normalize('NFC', filename)
    try:
        mid = mido.MidiFile(normalized_name)
    except FileNotFoundError:
        print(f"❌ 找不到檔案：[{normalized_name}]")
        continue

    segment_events, abs_time = [], 0.0
    for msg in mid:
        abs_time += msg.time
        if msg.type in ['note_on', 'note_off']:
            segment_events.append((abs_time, msg.copy()))

    if not segment_events: continue
    first_time, last_time = segment_events[0][0], segment_events[-1][0]
    for note_time, msg in segment_events:
        all_notes.append((current_timeline + (note_time - first_time), msg))

    actual_duration = last_time - first_time
    current_timeline += actual_duration + GAP_SECONDS

all_notes.sort(key=lambda x: x[0])
last_time = 0.0
for note_time, msg in all_notes:
    delta_ticks = int(mido.second2tick(max(0.0, note_time - last_time), ticks_per_beat=480, tempo=500000))
    msg.time = delta_ticks
    merged_track.append(msg)
    last_time = note_time

merged_track.append(mido.MetaMessage('end_of_track', time=0))
merged_mid.save(OUTPUT_FILE)
print(f"🎉 《光的戰役》8 段全數無縫拼接完成：{OUTPUT_FILE}，總時長：{merged_mid.length:.2f} 秒")

💡 工程價值：當實體交互遭遇物理人體工學瓶頸、檔案系統面臨 Unicode 多語系編碼壁壘、或需要精準調配樂句呼吸感時，工程師懂得善用代碼建立自動化工作流，在二進制與事件層面精準拼裝出無瑕疵的作品。

🎼 5. 演奏調性特調與音域物理探討（-1 vs +11）

💡 演奏調性特調說明：
為了在行動裝置狹小的螢幕上確保雙拇指彈奏的最高精確度與流暢度，本清單中的某些曲子並非按照原調演奏，而是由我改編為最適合鍵盤指法特徵的 C 大調進行實體錄製（例如：原本為 B 大調的《不敗的英雄》、以及原本為 降 D 大調的《淡淡的愛意》，錄音主體皆已統一轉為 C 大調）。

讀者若想聆聽原汁原味的原曲調性，只需在下方控制台的「選擇升降調」選單中，動態切換至對應的半音偏移量（例如：《不敗的英雄》選擇 -1 即可動態還原為 B 大調），這正是本專案「即時移調演算法」與「演奏數據化」的核心實用價值所在！

🤔 為什麼要改用負數（-1），而不是原本的升調（+11）？（聲學物理與體感痛點）
雖然在純數學與名義樂理上，「降 1 個半音（-1）」與「升 11 個半音（+11）」在音名上是等音對應（例如 C 降半音是 B，C 升 11 個半音也是高八度的 B）。但在數位音訊的實際播放中，兩者會帶來完全不同的災難性聽感：

1. 音域暴走失真（Octave Displacement）：如果選用 +11，程式會硬生生把所有音符集體往上提拉接近一個完整的八度。這會把我原本在舒適中音區、帶著厚實情感錄製的拇指演奏，強行逼入極高音的「尖銳區」，聽起來會變得單薄、刺耳，完全失去原曲該有的熱血與宏大感。

2. 還原真實音頻頻率：改用 -1 時，音符僅僅是微幅向下修正一個半音，維持在原本演奏的同一個八度音域內。這樣能完美保留我當初模擬實體鋼琴與戰隊電子琴時的飽滿中低音基頻，確保聽覺效果流暢、自然且完全不失真。

💡 8. 結語：從「數據結構」到「聲學靈魂」的工程實踐

數位音樂工程的迷人之處，在於它既是精密的純粹數學，也是充滿情感的聽覺藝術。回顧整套系統的架構設計，本專案將抽象的樂理與感性的演奏，逐層沉澱為扎實的前端工程實作：

  • 在底層協議與數據管線層：透過將二進位 MIDI 訊息解構為 (Pitch, Velocity, Time Offset) 陣列，確立了音訊驅動的單一真實數據源（Single Source of Truth）；在面對長篇曲目與複雜交響樂句的生理限制時，運用 Python（mido）實作分治重組工作流並精確配置段落銜接緩衝（Gap Padding），在消除冗餘發呆時間的同時保留樂曲的呼吸感；同時診斷並攻克多語系編碼壁壘，深入剖析 Unicode 規範化（NFC vs NFD）在 Windows 檔案系統下引發日文濁音/促音「幽靈空格」與 I/O 阻斷的成因，確立「後端管線 ASCII-Safe、前端 UI 在地化呈現」的跨平台架構規範，為後續的轉調、時鐘映射與視覺化提供堅實基石。
  • 在訊號合成與排程層：摒棄單純調用靜態音訊檔案（如 MP3/WAV）的常規做法，全面採用 Web Audio API 的 OscillatorNode 物理訊號產生器與 ADSR 包絡線動態運算；更透過 Tone.Transport 抽象主控時鐘，徹底解決非阻塞式排程、精準暫停與任意時間軸跳轉（Seek）的難題。
  • 在可視化與聲學層：將時域（Time Domain）的連續波形振幅映射為動態示波器，並利用快速傅立葉變換（FFT）即時拆解各諧波分貝能量，讓聲音的「物理實體」與「諧波色彩」在畫布上具象化呈現。
  • 在演奏數據與工程哲學層：演算法可以輕易完成即時轉調與音色變換，但真正賦予這些數位波形生命力的，始終是雙拇指在狹小螢幕上克服高密度節奏時所刻印下的細微時序動態與力度起伏。當物理環境遭遇極限時，工程師懂得善用代碼搭建自動化工具，守護演奏數據中最真實的人性靈魂。

當我們能以計算機科學的視角剖析音訊、用嚴謹的前端架構實現聲學互動，並以多年淬鍊的演奏手感作為數據基石時，技術與音樂便不再是彼此平行的領域，而是交融為兼具工程深度與藝術溫度的完整作品。
