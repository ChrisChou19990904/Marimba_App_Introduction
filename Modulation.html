💡 1. 數位音訊合成與轉調原理

本網頁底層基於 Tone.js 網頁音訊架構（Web Audio API），核心運作包含以下物理與數學邏輯：

(1) JavaScript 即時轉調演算法

在數位音樂（MIDI）協議中，每個音階都對應一個 0 到 127 的整數 MIDI Number。
本程式透過算術運算達成即時轉調：在音符觸發前執行 note.midi + transpose。
例如：原本演奏錄製的 C4 (MIDI 編號 60) 加上 3 個半音（transpose = 3），數值會變為 63 (D#4)，再由音訊引擎將該編號換算成對應的物理頻率（Hz）發聲。

(2) 波形合成（Oscillator）與包絡線（Envelope）

網頁能切換不同的聲音類型，是透過改變訊號產生器（Oscillator）的物理波形與振幅包絡線（ADSR Envelope）來模擬不同樂器的聽感：

  • 圓潤鋼琴風 (Triangle)：使用三角形波。其奇數諧波衰減極快，音色相對圓潤純淨。搭配快攻擊（Attack）、長釋放（Release）的包絡線，能有效模擬鋼琴或打擊樂器敲擊後餘音繚繞的物理動態。
  • 明亮電子琴 (Sawtooth)：使用鋸齒波。它包含了所有的連續諧波，聲音非常明亮且飽滿，是 80 年代昭和特攝電子合成器（Synthesizer）最經典的標誌性音色。
  • 復古 8-bit (Square)：使用方波。僅包含強烈的奇數諧波，聲音生硬且帶有強烈的數位感，能完美還原早期紅白機（NES）遊戲音樂的復古氛圍。
  • 柔和純音 (Sine)：使用正弦波。它是最純粹的單一頻率基音，沒有任何諧波成分，聽感極度平滑。

📊 2. 聲學可視化與時間軸排程控制原理

為了克服純音訊播放時「看不見數據流動」與「無法自由掌控播放時間」的限制，本架構引入了 Web Audio API 的進階分析節點與排程引擎：

(1) 示波器波形圖（Tone.Waveform）：時域分析

Tone.Waveform 能夠以每秒數十次的頻率捕捉訊號的時間域振幅（Time-Domain Amplitude）。程式將採集到的 -1.0 至 1.0 浮點數陣列映射至 Canvas 畫布的 Y 軸座標，繪製出連續振動的聲波線條。讀者可以直觀看見三角波的平緩折角、方波的垂直陡升，以及正弦波的柔和圓弧。

(2) 頻譜分析儀（Tone.FFT）：頻率域分析

Tone.FFT 透過快速傅立葉變換，將複雜的音訊訊號拆解為各頻率成分的能量分貝值（dB）。畫面左側代表低音貝斯（Bass）能量，右側代表高音與泛音（Treble）。當播放明亮的鋸齒波時，右側高頻柱會活躍跳動；轉調時，整個能量群則會即時水平平移。

(3) Tone.Transport 與 Tone.Part：非阻塞式時間軸主控

傳統做法如果直接呼叫 triggerAttackRelease，會將所有音符一次性鎖死在硬體時鐘上，導致無法暫停與拖曳。本系統改寫為：

  • 時間座標抽象化：將整首曲目的音符解析為帶有時間標籤的事件群組，載入至 Tone.Part。
  • 主控時鐘掛載：由 Tone.Transport 統籌全域播放指針。按下暫停時，僅需凍結時鐘並呼叫 releaseAll() 釋放發聲，即可完全不漏拍地保留當前播放進度。
  • 任意跳轉（Seek）：拖曳進度條時，透過更新 Tone.Transport.seconds 數值，即時對齊時間指針，達成流暢的快進與倒帶。

📱 3. 行動裝置瀏覽發聲重要提示與 Web Audio 底層原理

⚠️ 行動裝置瀏覽重要提示：
當你使用手機瀏覽本網頁時，請務必將手機側邊的「實體靜音開關」切換至響鈴模式（並確認非震動/勿擾狀態），否則網頁會完全沒有聲音。

💡 為什麼開啟靜音模式會導致網頁沒聲音？（技術原理探討）
本網頁是利用 HTML5 的 AudioContext（Web Audio API）在前端即時動態運算並合成物理波形。在 iOS（WebKit 核心）與部分 Android 系統的底層音訊通道設計（Audio Session Category）中，網頁端即時合成的音訊預設會被標記為 Ambient（環境音效）或次要媒體類別。

當手機開啟實體靜音鍵時，行動作業系統為了不干擾使用者，會在硬體層級強制壓制所有 Ambient 類別的音訊輸出（如同手機遊戲的背景音效會在靜音模式下被切斷，但 YouTube 等預錄影片所使用的 Playback 類別音訊不會被切斷）。因此，這並非程式出錯，而是作業系統的硬體機制攔截。點擊播放前請確保已切換為響鈴狀態！

⚠️ 4. 核心觀點：技術無法取代演奏能力

雖然程式可以透過演算法輕鬆改變調性與音色，但「優質的旋律數據」必須源於真實且紮實的演奏功底。
本網頁所展示的 48 首精選旋律，皆是我本人純手工在行動裝置狹小的螢幕上，完全僅憑「左手大拇指與右手大拇指」的極限協調，在 Perfect Piano 中開啟 MIDI 錄製模式辛苦彈奏而成，絕非使用網路上現成的數位音訊檔案。

在小螢幕上以雙拇指精準駕馭如《魔彈戰記龍劍道》或《假面騎士 Build》等每分鐘超過 130 拍（BPM）、音符密度極高的快節奏特攝曲目，要求創作者具備極高的節奏感、動態掌控力與鍵位空間感。這些親自演奏錄製的 MIDI 數據，完整保留了人類演奏特有的細微情感，是純程式動態生成或死板的 Q 點量化所無法比擬的。

🎼 5. 演奏調性特調與音域物理探討（-1 vs +11）

💡 演奏調性特調說明：
為了在行動裝置狹小的螢幕上確保雙拇指彈奏的最高精確度與流暢度，本清單中的某些曲子並非按照原調演奏，而是由我改編為最適合鍵盤指法特徵的 C 大調進行實體錄製（例如：原本為 B 大調的《不敗的英雄》、以及原本為 降 D 大調的《淡淡的愛意》，錄音主體皆已統一轉為 C 大調）。

讀者若想聆聽原汁原味的原曲調性，只需在下方控制台的「選擇升降調」選單中，動態切換至對應的半音偏移量（例如：《不敗的英雄》選擇 -1 即可動態還原為 B 大調），這正是本專案「即時移調演算法」與「演奏數據化」的核心實用價值所在！

🤔 為什麼要改用負數（-1），而不是原本的升調（+11）？（聲學物理與體感痛點）
雖然在純數學與名義樂理上，「降 1 個半音（-1）」與「升 11 個半音（+11）」在音名上是等音對應（例如 C 降半音是 B，C 升 11 個半音也是高八度的 B）。但在數位音訊的實際播放中，兩者會帶來完全不同的災難性聽感：

1. 音域暴走失真（Octave Displacement）：如果選用 +11，程式會硬生生把所有音符集體往上提拉接近一個完整的八度。這會把我原本在舒適中音區、帶著厚實情感錄製的拇指演奏，強行逼入極高音的「尖銳區」，聽起來會變得單薄、刺耳，完全失去原曲該有的熱血與宏大感。

2. 還原真實音頻頻率：改用 -1 時，音符僅僅是微幅向下修正一個半音，維持在原本演奏的同一個八度音域內。這樣能完美保留我當初模擬實體鋼琴與戰隊電子琴時的飽滿中低音基頻，確保聽覺效果流暢、自然且完全不失真。

💡 8. 結語：從「數據結構」到「聲學靈魂」的工程實踐

數位音樂工程的迷人之處，在於它既是精密的純粹數學，也是充滿情感的聽覺藝術。回顧整套系統的架構設計，本專案將抽象的樂理與感性的演奏，逐層沉澱為扎實的前端工程實作：

  • 在底層協議層：透過將二進位 MIDI 訊息解構為 (Pitch, Velocity, Time Offset) 陣列，確立了音訊驅動的單一真實數據源（Single Source of Truth），為後續的轉調、時鐘映射與視覺化提供堅實依據。
  • 在訊號合成與排程層：摒棄單純調用靜態音訊檔案（如 MP3/WAV）的常規做法，全面採用 Web Audio API 的 OscillatorNode 物理訊號產生器與 ADSR 包絡線動態運算；更透過 Tone.Transport 抽象主控時鐘，徹底解決非阻塞式排程、精準暫停與任意時間軸跳轉（Seek）的難題。
  • 在可視化與聲學層：將時域（Time Domain）的連續波形振幅映射為動態示波器，並利用快速傅立葉變換（FFT）即時拆解各諧波分貝能量，讓聲音的「物理實體」與「諧波色彩」在畫布上具象化呈現。
  • 在演奏數據層：演算法可以輕易完成即時轉調與音色變換，但真正賦予這些數位波形生命力的，始終是雙拇指在狹小螢幕上克服高密度節奏時所刻印下的細微時序動態與力度起伏。這是冷硬的程式碼所無法憑空生成的真實靈魂。

當我們能以計算機科學的視角剖析音訊、用嚴謹的前端架構實現聲學互動，並以多年淬鍊的演奏手感作為數據基石時，技術與音樂便不再是彼此平行的領域，而是交融為兼具工程深度與藝術溫度的完整作品。
